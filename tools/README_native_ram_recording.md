# Opt-in native RAM window

`request_analysis_capture.ps1 -TargetProcessId <pid> -ExpectedExecutable <exact-path> -Action RamWindow -DurationSeconds 20 -RamMiB 512`

This explicit diagnostic command does not change profiles or presentation. No RAM window exists until requested. Supported duration is 1–120 seconds; private pixel budget is 1–16384 MiB. The request is rejected if the budget plus bounded event metadata exceeds half of currently available physical RAM. Memory is allocated lazily on a copier thread, with a 1 GiB available-memory reserve. The event ledger is limited to 65,536 offers (14.5 MiB in the x64 build); small queue/deque metadata is additionally bounded by that limit. A source larger than the requested pixel budget is recorded as invalid and is not retained.

The accepted-input tap offers original source identities independently of optional analysis or render selection. It does not perform a pixel scan, GPU upload, or native pixel copy. At most two additional source owners are held, including the active copy. Admission is bounded and does not wait for the copier or storage. Ordinary native sources are supported; unavailable canonical sources, including Dolby Vision tunnel input at this tap, appear as invalid-source events. This does not affect existing sampled/consecutive captures.

A private RAM ring holds the newest fitting source frames. On overwrite, the original event becomes `ram-evicted`. At acquisition end, the diagnostic writer writes the retained window to the existing `.bin`/`.txt` native format. Disk throughput cannot stall acquisition because draining starts afterward. It can delay completion of the diagnostic command's output; status reports captureWriting until finished. Shutdown cancels queued disk writes rather than flushing the entire RAM window; an already executing filesystem write is not forcibly cancelled. Changing source context ends this native window and retains the preceding valid frames.

`native-window.jsonl` contains every admitted metadata offer and its final outcome, including pressure/retain failures, original identity, RAM eviction, and disk write failure. Event-cap overflow is counted explicitly. Never infer a complete sequence from a frame count: inspect identities and gaps. `frames.jsonl` and original sidecars describe written frames. Picture bounds and subtitle detector settings are unavailable at the accepted-input tap and explicitly marked unavailable; zero placeholders are not measured picture or semantic authority.

Run `python tools/inspect_native_ram_recording.py <session-directory> --output <receipt.json>` after captureWriting becomes false. This validates all claimed-written files, identity sidecars, hashes, and retained source gaps. It does not interpolate missing frames or claim uninterrupted HDMI recording. Files from a failed write may exist without a successful index entry and must not be treated as complete frames.

At 3840×2160 V210 (22,118,400 bytes/frame), 512 MiB retains 24 frames: approximately one second at 24 fps or 0.4 seconds at 60 fps. Longer windows require proportionally more explicitly requested RAM. Recorder tests and offline capacity measurements are not proof of live capture/display deadlines; real hardware omissions remain possible and must be reported.
