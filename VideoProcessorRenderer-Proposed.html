VideoProcessor VP-0028 renderer configuration

VP-0028 side-by-side test build. The runtime now validates the unified graph before capture, resolves independent profile groups, supports one key selecting profiles in multiple groups, applies viewport profiles, fingerprints effective settings, commits versioned per-config state after a successful build, and schedules generation-scoped refresh actions. Keep the released configuration untouched and launch the test configuration with /vr_config "VideoProcessorRenderer.vp0028-test.cfg".

The proposal replaces separate display rules, rule shortcuts, screen-profile shortcuts, and refresh-rate command maps with one configuration vocabulary: named profiles whose ordinary when= expressions may include a key condition, and completed-transition event actions. It is designed for streaming sources, where stable capture metadata is available but filenames, codecs, bitrates, and library metadata are not reliable inputs.

Configuration model

Every renderer setting starts with the base [display] section. Four independent profile groups then supply their own overrides. Each group has exactly one active profile, and a profile may change only settings owned by that group.

[display] base
  -> input profile
  -> scaling profile
  -> display profile
  -> viewport profile
GroupSelectionOwns
inputNormally automatic from source metadataTone mapping, gamut mapping, peak detection, contrast recovery, SDR input transfer
scalingNormally automatic from source geometryQuality/scalers, proposed sigmoid choice, proposed named deband strength, dithering
displayNormally manualCalibrated output target, nits/black, DXGI output contract, display signaling, LUT
viewportNormally manualNormal/scope selection and scope geometry

A group in automatic mode selects the matching profile with the highest priority; equal priorities use the most source comparisons in the matching branch, then the group’s explicit profile-list order. A profile without when= is default-only. No fake condition such as $width==0 is required.

Required implementation pipeline

parse once
  -> validate complete graph
  -> load one selection mode per group
  -> evaluate source/key event
  -> resolve typed settings by ownership
  -> compare effective-settings fingerprint
  -> apply successfully
  -> persist committed manual selections

The parser produces a platform-independent configuration model and one reusable expression AST. The GUI delivers canonical key events but does not interpret expressions or choose profiles. Parsing, selection, persistence, and event scheduling must be unit-testable without a D3D device, capture card, window, or libplacebo runtime.

This follows established configuration practices: strict unknown-field validation, an explicit versioned public contract, deterministic ordered declarations, one source of truth for expressions, transactional state commits, and observable transition identities. Useful reference points are JSON Schema object validation, strict API field validation, versioned public APIs, and Windows application accelerators.

[general] and profile groups

[general] owns renderer-session policy rather than profile settings: profile-selection persistence defaults, refresh switching, default event delay, and diagnostic-only controls. The four built-in groups have a fixed order: input, scaling, display, viewport. Each group section chooses its startup selection, explicitly lists profiles, and may override persistence.

[general]
 # Optional; omitted means the latest supported unified schema.
 # config_version=2
persist_profile_selection=true
switch_refresh_rate=true
event_action_delay_seconds=5

[profile_groups.input]
profiles=sdr,pq_hdr,hlg_hdr,lldv_like
default=auto
# A group-level key condition returns this group to automatic selection.
when=$key=="Ctrl+F4"

[profile_groups.display]
profiles=rec709_projector,bt2020_projector
default=rec709_projector
persist_profile_selection=true

Each group explicitly lists profiles to preserve deterministic review order and reject orphan sections. Startup precedence is a valid persisted manual profile, then the configured default, then no override when an automatic group has no match. Persistence is enabled by default; a group may disable it.

state_version=2
screen_profile=scope
profile.display=rec709_projector
profile.viewport=scope

The state file stores committed manual choices only and preserves a compatible screen_profile= mirror. The default config retains VideoProcessorRenderer.state; an explicit /vr_config X.cfg uses sibling X.state, isolating manual tests. Writes use temporary-file replacement and occur only after successful application; a failed renderer change leaves previous active and persisted selections intact.

Profiles

Profiles use the section name [profiles.<group>.<name>]. Only settings owned by the group are accepted; an unknown key or a valid key in the wrong group is a startup validation error.

[profiles.input.pq_hdr]
when=$transfer==PQ
priority=100
tone_mapping=spline
gamut_mapping=perceptual
peak_detection=high_quality
contrast_recovery=0.25

[profiles.display.rec709_projector]
# This is a manual display selection, not an impossible source condition.
when=$key=="F5"
sdr_target_primaries=REC709
sdr_target_nits=100
sdr_black_nits=0
output_range=FULL
output_gamma=AUTO
lut=lut\Projector-Rec709.cube
lut_reference_primaries=REC709
lut_reference_transfer=BT1886
lut_reference_range=FULL
lut_reference_nits=100

Strict validation and application

Unified mode rejects unknown or duplicate groups, profiles, sections, and keys; missing or orphan sections; invalid defaults and priorities; unavailable variables; wrong-group settings; unsupported values; duplicate canonical key chords; and mixed legacy/unified syntax. Names have a bounded identifier grammar, priorities default to zero with a documented range, and every renderer key has a type, allowed values/range, owner, and apply class. Profile strings are converted into typed settings before renderer creation. Rebuild decisions compare effective typed-value fingerprints rather than profile labels.

Application is transactional: VP resolves a candidate without mutating active state, builds one replacement renderer for all rebuild-class changes, and commits only after readiness. Viewport updates apply the complete group atomically. Failure retains the previous renderer, viewport, selections, state file, and event identity.

Automatic source conditions

Automatic profile conditions read only stable capture facts. They support ==, !=, <, <=, >, >=, &&, ||, !, and parentheses. Names and text values are case-insensitive.

VariableExample values
$transferSDR, PQ, HLG, HDR, UNKNOWN
$primariesREC709, BT2020, P3_D65
$rangeFULL, LIMITED, UNKNOWN
$cadenceExact named cadence: 23.976, 24, 25, 29.97, 30, 50, 59.94, 60
$width, $height, $resolutionCapture raster, for example 3840x2160
$scanPROGRESSIVE or INTERLACED
$formatV210, UYVY, R10B, R12L
$hdr_metadatatrue only when valid static HDR metadata is present
$keyTransient hotkey chord for a key-selection event, for example "F5" or "Ctrl+F4"; otherwise NONE
Cadence is exact. It is not a truncated integer and not a floating-point comparison. 23.976 and 24000/1001 may be accepted as equivalent spellings, with one canonical value in diagnostics.

Mastering data, MaxCLL, and MaxFALL remain renderer inputs, rather than ordinary rule variables. Output refresh is deliberately excluded: it is a result of profile selection and display switching, not an input to either.

Key conditions and persistence

All direct selection uses the normal when= grammar. In normal source-state evaluation $key is NONE. When a hotkey arrives, VP evaluates the same parsed AST with $key set to its canonical chord and source variables from one immutable snapshot. The AST exposes referenced chords for accelerator registration; the GUI does not use a second regex grammar. $key permits only equality against quoted literal chords.

[profiles.display.rec709_projector]
when=$key=="F5"

[profiles.display.bt2020_projector]
when=$key=="F6"

[profiles.viewport.normal]
when=$key=="F2"

[profiles.viewport.scope]
when=$key=="F3"

These are application-local accelerators, not system-wide hotkeys. They fire only while the active VP window’s UI thread processes keyboard messages and preserve existing dialog/control behavior. In a group section, when=$key==... returns that group to automatic selection. One canonical chord may select one profile in each independent group (or reset one or more groups), so one key can deliberately choose matching input, scaling, display, and viewport profiles together. Two matching profiles in the same group remain a startup error. Unregistrable chords and reset conditions for groups that cannot be automatic are also errors. The complete profile expression is evaluated, and repeat messages are ignored until key-up.

[event_actions] — completed refresh events

Actions are not profiles and cannot influence selection. They observe a completed display transition and may schedule one trusted local command after a bounded delay.

[event_actions]
actions=audio_delay_24,audio_delay_60,restore_audio

[event_actions.audio_delay_24]
on=refresh.applied,refresh.confirmed
when=$actual_refresh==23.976 || $actual_refresh==24
program=C:\Videoprocessor\audio\audio_delay.bat
arguments=315

[event_actions.restore_audio]
on=refresh.restored
when=$actual_refresh==60
delay_seconds=0
program=C:\Videoprocessor\audio\audio_delay.bat
arguments=0
EventMeaning
refresh.appliedVP changed the mode and Windows reported the resulting rate.
refresh.confirmedThe requested rate was already active; no mode change was needed.
refresh.restoredRenderer shutdown successfully restored VP’s captured prior rate.

Failed or unsupported refresh requests run no action. An event action without delay_seconds= inherits [general] event_action_delay_seconds; a per-action value overrides it. Every completed transition has generation and transition IDs. A session-level scheduler deduplicates each action by those IDs, cancels superseded applied/confirmed work, and remains alive long enough to complete a successful restoration action. Rate matching uses canonical rational families, never truncated integers or direct floating-point equality.

program=, literal arguments=, and optional working_directory= replace free-form command lines. Executables launch directly with Unicode process creation; batch files use an explicitly quoted %ComSpec% /d /s /c path. No source interpolation occurs. Actions launch asynchronously in declared order outside the render thread. With refresh switching disabled, no refresh event is emitted.

Diagnostics and testing

Logs show configuration mode/version, canonical key bindings, persistence policy, the effective profile and origin for every group, changed-setting groups, fingerprints, and event generation/transition IDs. The unified path is not deployable until automated tests cover strict parsing, deterministic resolution, source/key combinations, per-group state, failed-apply rollback, viewport behavior, exact refresh families, event cancellation/deduplication, and unchanged legacy behavior.

Initial streaming profile library

input:   sdr | pq_hdr | hlg_hdr | lldv_like
scaling: sd_hd | mid | uhd_native | optional manual performance diagnostic
display: rec709_projector | bt2020_projector
viewport: normal | scope

Use curated renderer controls: existing tone/gamut mapping, quality/scaler selection, peak detection, contrast recovery, and dithering; proposed named deband strengths; and proposed SDR-only sigmoid scaling. The proposal does not add raw tone/gamut constants, custom shader hooks, frame mixing, inverse tone mapping, libplacebo deinterlacing, or subjective brightness/hue controls.

madVR and libplacebo comparison

The design keeps madVR’s useful concepts—named profiles, automatic rules, independent areas, manual selection, and persistence—but makes ordering explicit, restricts selectors to stable streaming capture facts, validates group ownership, and logs one reproducible effective selection. It keeps libplacebo behind a curated typed-policy boundary: VP resolves one immutable settings snapshot at a safe transition, rather than exposing raw structures or per-frame tuning as configuration.

Review sample and migration

Open the minimal resolver example, the complete target example, or the ported legacy renderer configuration. All are explicitly non-deployable until implementation is complete.

An explicit config_version or any unified section selects strict unified mode. In that mode an omitted config_version means the latest schema supported by that VP build (currently 2); an explicit value must be supported. A file with neither uses the unchanged legacy parser. Mixing [display_rules], [shortcuts], or [refresh_rate_commands] with unified sections is an error rather than an undocumented precedence rule. Only single-owner legacy records have a mechanical conversion; multi-owner display rules require operator redesign or remain in legacy mode. VP never rewrites the active configuration; any future migration tool writes a side-by-side file.
