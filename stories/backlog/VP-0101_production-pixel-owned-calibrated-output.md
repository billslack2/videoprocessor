# VP-0101: Implement production pixel-owned calibrated output and 3D LUTs

## Status

Backlog. This is the single remaining production story for exact Alpha SDR
output and calibrated target-frame 3D LUT workflows. It must not move to In
Progress until VP-0100 records an accepted pixel-preserving presentation
contract and VP-0096's applicable range-correct conversion work is accepted.

No implementation branch has been selected. Before source work starts, query
the current default branch of `billslack2/videoprocessor`, report it to the
developer, and obtain explicit confirmation of that implementation base under
the tracker workflow.

## User story

As a calibrated-projector user, I want Alpha to render exact, declared SDR
gamma, gamut, and range values either directly to my calibrated display mode or
through a matching cached 3D `.cube` calibration LUT, so Rec.709, BT.2020, and
P3-D65 workflows reach the projector without an unintended post-render color
conversion.

## Outcome

Implement the production mode proven by VP-0100 while retaining VP-0011's
current DXGI-contract-locked behavior as the compatibility fallback. The new
mode must support a direct calibrated feed and a target-frame calibration LUT;
both use the same explicit color-contract model and validation boundary.

This story consolidates the remaining useful work from VP-0029, VP-0047, and
VP-0048. Those records remain in Will Not Do for history and must not be
implemented separately.

## Required color-contract model

Configuration, policy, logs, OSD, tests, and documentation must represent these
separate domains explicitly:

1. **Source contract**: the actual captured input format and metadata.
2. **Reference render/LUT-input contract**: primaries, transfer, range,
   reference white nits, black level, and gamut/tone-map policy generated by
   libplacebo immediately before an optional calibration LUT.
3. **Post-LUT native-drive contract**: the projector-native values produced by
   the LUT. These values are opaque calibrated drive values unless the profile
   explicitly defines otherwise; they must not be relabeled P3, Rec.709, or
   BT.2020 merely from the LUT-input domain.
4. **Presentation transport contract**: the exact swapchain format/tag,
   presentation mode, Windows state, GPU state, and verification identity
   selected from VP-0100's accepted result.
5. **Physical output/signaling contract**: the range and signaling emitted by
   the GPU and the projector/native mode the installation must select.

Every active profile must resolve all applicable fields. `AUTO` must have one
documented deterministic meaning per field and must never silently substitute
sRGB for pure gamma 2.2, reinterpret BT.2020 coordinates as P3, or accept a LUT
whose declared input differs from the generated reference target.

## Scope

1. Add a production output-policy mode that uses only a presentation transport
   accepted by VP-0100. Keep the current contract-locked policy as the default
   compatibility fallback and fail closed whenever required state cannot be
   verified or has been invalidated.
2. Allow libplacebo's exact supported SDR output encodings through the new
   policy only where VP-0100 proved them. Candidate transfers include BT.1886,
   sRGB, and pure power gamma 1.8-2.8; candidate primaries include Rec.709,
   BT.2020, and P3-D65; candidate ranges include full and limited. The shipped
   list must be the proven subset, not every parsable cross-product.
3. Support direct calibrated output with no LUT. The display profile must state
   the expected display/projector mode and exact render contract, while the OSD
   distinguishes render encoding, transport, and physical signaling.
4. Extend the existing VP-0011 cached target-frame `PL_LUT_NATIVE` path to
   accept calibration profiles whose reference target differs from any named
   DXGI declaration, but only through VP-0100's proven transport.
5. For HDR input, preserve BT.2020/PQ or HLG as the source representation and
   tone/gamut map to the configured SDR reference target before the LUT. P3
   mastering metadata or the fact that most HDR content lies within P3 does
   not change the source coordinates.
6. Implement P3-D65 as a first-class render/LUT-input target. Perform primaries
   conversion in linear light through libplacebo's color pipeline. Apply the
   selected gamut-mapping policy at the output-target boundary: offer a
   documented clipping/colorimetric mode and a documented roll-off/perceptual
   mode for real or decoded values outside P3. Do not hard-code an early
   BT.2020-to-P3 matrix that clips legitimate BT.2020 content.
7. Apply the calibration cube only after source decoding, tone mapping, gamut
   mapping, reference-target transfer encoding, and range encoding. After the
   LUT, perform no unrequested gamut, transfer, range, tone-map, ICC, or desktop
   color conversion.
8. Preserve VP-0011's bounded parsing, safe path handling, 3D-only validation,
   dimension/resource limits, caching, rule selection, render-thread ownership,
   teardown, device recreation, and no-LUT recovery behavior.
9. Absorb VP-0029's final-dither question. Preserve the current safe behavior
   when the bundled D3D11/libplacebo path cannot combine a target LUT with
   error diffusion. If final error diffusion requires an intermediate/two-pass
   path, prove identical first/second-pass color metadata, identity of the
   second color transform, correct LUT-before-final-dither order, acceptable
   4K23.976 and 4K59.94/60 performance, and deterministic failure fallback.
   Do not add a second pass merely to close the old story.
10. Reverify or fall back after fullscreen/window changes, refresh changes,
    display reconnect, Windows HDR/Advanced Color changes, GPU reset, driver
    state change where detectable, renderer restart, and profile/rule change.
11. Add concise diagnostics for requested and accepted render target, LUT input,
    LUT file/dimensions/status, post-LUT native profile, transport mode,
    swapchain declaration, driver/output range, physical signaling where known,
    and fallback/rejection reason.
12. Update the shipped sample configuration and `CONFIGURATION.html` with every
    supported field/value, `AUTO` semantics, valid combinations, calibration
    assumptions, P3/BT.2020 explanation, direct-feed and LUT examples, fallback
    behavior, and a reproducible verification checklist. Do not ship a user's
    LUT or projector-specific settings.

## Configuration design requirements

- Continue using the canonical `vpvr` display/profile/rule namespace and its
  existing inheritance model; do not create a second renderer configuration
  file or a parallel rule system.
- A profile must declare whether it requires pixel-owned output or allows the
  compatibility fallback. If fallback would invalidate the calibration
  contract, reject the LUT/direct profile and continue ordinary safe playback
  rather than calling it calibrated.
- LUT input fields must include primaries, transfer, range, reference white
  nits, and black level where the selected curve depends on it. BT.1886 must
  document its authoring black/white assumptions.
- Projector/native output labels are descriptive installation requirements and
  must not cause a hidden post-LUT transform.
- Existing valid VP-0011 Rec.709/BT.2020 profiles retain their behavior unless
  the user explicitly selects the new mode.

## Validation plan

1. Unit-test the valid and invalid cross-product of output mode, primaries,
   transfer, range, reference levels, LUT declaration, presentation transport,
   and fallback policy.
2. Add deterministic GPU tests for no LUT, identity LUT, diagnostic
   non-identity LUT, malformed/missing LUT, contract mismatch, and render
   failure. Cover endpoints, near-black/near-white, neutral ramps, and samples
   that distinguish sRGB, pure gamma 2.2, gamma 2.4, and range scaling.
3. Prove P3-D65 reference values at the LUT boundary. Use gamut-stress content
   outside P3 but inside BT.2020 to distinguish clipping from roll-off and to
   prove the source was not merely reinterpreted as P3.
4. Use VP-0100's physical-output method to confirm that direct output and LUT
   output preserve their expected post-render code values. Backbuffer readback
   alone is not final acceptance.
5. Validate SDR Rec.709 and HDR-to-SDR paths with at least one known calibration
   LUT and real projector/display mode. Include a P3-D65/gamma-2.2-to-native
   workflow if VP-0100 accepted that transport.
6. Exercise rule/profile switching, source EOTF and gamut changes, refresh and
   display-mode changes, renderer restart, GPU recovery, missing optional
   renderer components, and unsupported hardware. Verify accurate fallback and
   restoration without stale frames, wrong signaling, black screens, retry
   loops, leaks, or queue starvation.
7. Record Release|x64 build and complete automated test evidence plus GPU,
   driver, Windows state, projector/display mode, LUT provenance, measurement
   method, expected results, and actual results.

## Acceptance criteria

- A direct calibrated profile and a 3D-LUT profile activate only when their
  exact render/LUT-input and presentation transport contracts are verified.
- Pure gamma values are generated as pure power curves; sRGB remains explicitly
  piecewise and is never presented as arbitrary gamma 2.2.
- A P3-D65 LUT receives P3-D65 encoded RGB after proper tone/gamut mapping, not
  BT.2020 RGB whose content happens to be mostly P3.
- Post-LUT projector-native values reach the validated output path without an
  unrequested second color conversion and are not falsely labeled as a generic
  P3 wire signal.
- Full and limited profiles preserve their intended code range through physical
  output within the validated tolerance.
- Unsupported hardware/state/profile combinations fall back to VP-0011's safe
  ordinary output or no-LUT playback with an actionable reason; Alpha does not
  silently approximate a calibrated contract.
- Existing no-LUT and contract-locked LUT behavior remains unchanged unless the
  user selects the new mode.
- Documentation and diagnostics let an A/V-literate user distinguish source,
  render target, LUT input, native LUT output, transport, and physical
  signaling.
- The story is not Done until automated tests, Release|x64 build, and documented
  real-output/projector validation are accepted.

## Dependencies and disposition of older stories

- VP-0100 is a hard prerequisite and must provide an accepted presentation
  contract before implementation starts.
- VP-0096's applicable source/range conversion work must be accepted before
  production end-to-end calibration claims are made.
- VP-0011 and VP-0012 remain the completed contract-locked Phase 1 baseline.
- VP-0004, VP-0019, VP-0064, and VP-0093 define existing range, SDR BT.2020,
  persistence, signaling, and fallback behavior that must not regress.
- VP-0029, VP-0047, and VP-0048 are superseded by this story and VP-0100.

## Non-goals

- Do not add arbitrary LUT stacks, creative look LUTs, ICC management, or
  source-side LUT processing.
- Do not add 1D LUT stages in this story. Preserve an explicit future extension
  point for pre/post 1D calibration without exposing unimplemented settings.
- Do not claim universal NVIDIA, AMD, Intel, Windows, or display compatibility
  beyond the configurations validated by VP-0100 and this story.
- Do not control projector picture modes or overwrite deployed user
  configuration without explicit approval.
- Do not patch or upgrade libplacebo unless a separate approved dependency
  story establishes that requirement.
